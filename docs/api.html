Справочник REST API

Шесть эндпоинтов: тела запросов, все коды ответов, примеры curl и готовые фрагменты клиентского кода. Базовый адрес при локальном запуске — http://localhost:3000.

Общие правила

АспектПравило
ФорматЗапрос и ответ — JSON. Заголовок Content-Type: application/json обязателен для POST и PUT
Размер телаНе более 16 КБ, иначе 413
АутентификацияКука сессии sl.sid. В fetch нужен credentials: 'same-origin', в curl — -c/-b
Ограничение частоты20 запросов за 15 минут с IP на /api/register, /api/login, /register
Формат ошибкиВсегда { "success": false, "message": "…" } — текст пригоден для показа пользователю
СекретыПароль и passwordHash не возвращаются ни одним эндпоинтом

POST /api/register

POST Создаёт пользователя, хеширует пароль и сразу открывает сессию.

Тело запроса

ПолеТипОграничения
usernamestring3–32 символа: латиница, кириллица, цифры, _, ., -. Пробелы по краям обрезаются
passwordstring6–128 символов, не обрезается

Ответы

КодКогдаТело
201Пользователь создан{ success: true, message: "Регистрация успешна", user } + Set-Cookie
400Не прошла валидация{ success: false, message: "Логин: 3–32 символа…" }
409Логин занят (без учёта регистра){ success: false, message: "Пользователь с таким логином уже существует." }
429Превышен лимит попыток{ success: false, message: "Слишком много попыток. Повторите позже." }
500Ошибка записи файла и т.п.{ success: false, message: "Внутренняя ошибка сервера" }

POST /api/login

POST Проверяет пару логин-пароль через bcrypt.compare и открывает сессию.

КодКогдаКомментарий
200Успешный входТело: { success: true, message: "Вход выполнен", user }
400Пустые или некорректные поляТа же валидация, что и при регистрации
401Нет такого пользователя или неверный парольОтвет одинаковый специально — по нему нельзя определить, существует ли логин
429Больше 20 попыток за 15 минутЗащита от перебора
 
curl -s -X POST http://localhost:3000/api/login \
  -H 'Content-Type: application/json' \
  -c cookies.txt \
  -d '{"username":"hunter","password":"secret123"}'

GET /api/me

GET Возвращает пользователя, чей username лежит в сессии. Именно этим запросом главная страница определяет, показывать «Войти / Регистрация» или «Мой профиль».

curl -s -b cookies.txt http://localhost:3000/api/me
{
  "success": true,
  "user": {
    "username": "hunter",
    "profile": { "level": 1, "xp": 0, "skills": [] },
    "createdAt": "2026-09-04T17:37:17.017Z"
  }
}
{ "success": false, "message": "Не авторизован" }
401 — это норма

Для гостя 401 не ошибка, а штатный ответ. Страницы обрабатывают его тихо: главная просто оставляет надпись «Гость», userinfo.html предлагает перейти ко входу.

PUT /api/me/profile

PUT Сохраняет игровой профиль на сервере. Задел под синхронизацию прогресса между устройствами: эндпоинт готов и покрыт тестами, интерфейс пока пишет только в localStorage.

{
  "level": 3,
  "xp": 42,
  "skills": ["Память", "Дисциплина"]
}
КодКогда
200Профиль сохранён; в ответе обновлённый пользователь
400level < 1, xp < 0, нечисловые значения или skills не массив
401Нет сессии
 
curl -s -X PUT http://localhost:3000/api/me/profile \
  -H 'Content-Type: application/json' \
  -b cookies.txt \
  -d '{"level":3,"xp":42,"skills":["Память"]}'

POST /api/logout

POST Уничтожает сессию на сервере и удаляет куку. Всегда отвечает 200, даже если сессии не было — так клиенту не нужно обрабатывать особый случай.

curl -s -X POST -b cookies.txt http://localhost:3000/api/logout
# {"success":true,"message":"Выход выполнен"}

POST /register — устаревший

DEPRECATED Совместимость со старым клиентом: если логин уже существует — работает как вход, если нет — как регистрация. Новый код должен использовать явные /api/login и /api/register.

Почему такое поведение нежелательно

Клиент не знает, что именно произошло — вход или создание учётки. Опечатка в логине молча создаёт нового пользователя вместо ошибки «неверный пароль». Алиас оставлен только ради обратной совместимости.

Клиентские примеры

Вход из браузера

const response = await fetch('/api/login', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  credentials: 'same-origin',          // без этого кука не сохранится
  body: JSON.stringify({ username, password })
});

const result = await response.json().catch(() => ({}));

if (!response.ok || !result.success) {
  showMessage(result.message || 'Не удалось выполнить запрос.', 'error');
  return;
}

window.location.href = 'userinfo.html';

Две детали, которые легко упустить: .catch(() => ({})) защищает от ответа без JSON (например, HTML-страницы от прокси), а проверка идёт и по response.ok, и по result.success.

Проверка «кто вошёл»

fetch('/api/me', { credentials: 'same-origin' })
  .then(response => (response.ok ? response.json() : null))
  .then(result => {
    if (!result || !result.user) return;          // гость — просто ничего не меняем
    document.getElementById('regBtnLabel').textContent = 'Мой профиль';
    document.getElementById('regBtn').href = 'userinfo.html';
    document.getElementById('userInfo').textContent = result.user.username;
  })
  .catch(() => { /* офлайн-режим: остаёмся гостем */ });

Полный цикл в curl

BASE=http://localhost:3000

# 1. Регистрация — кука сохраняется в файл
curl -s -c jar.txt -X POST $BASE/api/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"tester","password":"secret123"}'

# 2. Кто я
curl -s -b jar.txt $BASE/api/me

# 3. Сохранить профиль
curl -s -b jar.txt -X PUT $BASE/api/me/profile \
  -H 'Content-Type: application/json' \
  -d '{"level":2,"xp":10,"skills":["Память"]}'

# 4. Выход
curl -s -b jar.txt -X POST $BASE/api/logout

# 5. Теперь снова 401
curl -s -b jar.txt $BASE/api/me
