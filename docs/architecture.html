Архитектура

Проект состоит из двух почти независимых половин: игровая логика целиком живёт в браузере, а сервер отвечает только за раздачу файлов и учётные записи. Ниже — как это связано и что происходит при каждом действии пользователя.

Ключевое архитектурное решение

Игра — клиентская

Навыки, задания, таймер и тренажёр не требуют сети. Всё состояние в localStorage, поэтому приложение работает офлайн и его можно выложить статикой.

Аккаунты — серверные

Пароль нельзя проверять на клиенте: любой сможет посмотреть исходник. Регистрация, вход и профиль — только через API, состояние входа держит httpOnly-кука.

Одно хранилище навыков

skills-store.js — единственный модуль, который знает формат данных. Обе игровые страницы работают через него, поэтому опыт из тренажёра попадает в навыки на главной.

Историческое противоречие, которое было устранено

В исходной версии login.html вообще не обращался к серверу — он вёл свой список пользователей в localStorage, а server.js вёл свой в users.json. Две «базы» не были связаны, а бэкенд фактически был мёртвым кодом. Теперь источник истины для учёток один — сервер. Подробности: Что изменилось.

Жизненный цикл HTTP-запроса

Порядок middleware в server.js определяет всё поведение сервера. Запрос проходит цепочку сверху вниз и останавливается на первом обработчике, который отправил ответ.

1. helmetПроставляет защитные заголовки. CSP и frameguard отключены: страницы тянут Tailwind с CDN и должны открываться во встроенном превью
2. express.jsonРазбирает тело JSON, лимит 16 КБ — защита от гигантских payload
3. sessionЧитает куку sl.sid, подставляет req.session
4. rate limitТолько на /api/register, /api/login, /register: 20 запросов / 15 минут на IP
5. Роуты APIВалидация → работа с users.json → JSON-ответ без пароля
6. express.staticЕсли ни один роут не сработал — отдаёт файл из корня репозитория
7. 404 для /apiНеизвестный метод API получает JSON, а не HTML-страницу
8. Обработчик ошибокЛогирует исключение и отвечает 500 без утечки стека

Почему два ключа localStorage

memoryTrainerData хранит именно прогресс дерева (какие уровни пройдены и сколько набрано «тренажёрного» XP) — это состояние экрана. levelUpData хранит навыки и задания, то есть общий прогресс игрока. Тренажёр пишет в оба: своё состояние — себе, награду — в общие навыки.

Что осознанно упрощено

  • Файл вместо базы данных. users.json читается и пишется целиком. Для десятков пользователей этого достаточно; запись атомарная (через временный файл и rename), но при тысячах записей и параллельных запросах нужен SQLite или Postgres.
  • Сессии в памяти. express-session использует MemoryStore по умолчанию: после рестарта сессии теряются, горизонтальное масштабирование невозможно. Для продакшена — Redis-store.
  • Игровой прогресс не синхронизируется между устройствами. Эндпоинт PUT /api/me/profile для этого готов, но интерфейс пока пишет только в localStorage; перенос — через кнопки экспорта и импорта JSON.
  • Tailwind с CDN. Удобно для одного файла без сборки, но в офлайне главная теряет стили и в консоли появляется предупреждение о непригодности CDN-сборки для продакшена.
