Хранение паролей

форма login.html │ password: "secret123" ▼ POST /api/register (тело запроса, HTTPS в продакшене) │ ▼ bcrypt.hash(password, 10) │ ▼ users.json: "passwordHash": "$2a$10$XokiFmmJfv9Kug…" ^^^^^^^^^^^^^^ ни пароля, ни возможности его восстановить пароль НЕ попадает: в лог, в ответ API, в localStorage, в URL, в Git

bcrypt выбран сознательно: он медленный по замыслу и включает соль в сам хеш, поэтому радужные таблицы и сравнение одинаковых паролей между пользователями не работают. Стоимость 10 (около 2¹⁰ итераций) — стандартный компромисс между временем ответа и стойкостью; её можно поднять переменной BCRYPT_ROUNDS.

Что было до аудита

Пароль хранился строкой и в users.json, и в localStorage браузера, а сервер возвращал в ответе весь объект пользователя вместе с паролем. Любой человек с доступом к файлу, к DevTools или к перехваченному ответу получал готовые учётные данные — и, скорее всего, те же пароли от других сервисов.

Выход (POST /api/logout) вызывает req.session.destroy() — запись удаляется на сервере, поэтому украденная ранее кука после выхода бесполезна.

Защита от XSS

Единственное место, где в интерфейс попадают данные, введённые пользователем и хранящиеся на сервере, — экран профиля. Раньше он собирался конкатенацией строк:

userInfoDiv.innerHTML = `
  <p><strong>Логин:</strong> ${userData.username}</p>
`;

Логин вида <img src=x onerror=alert(document.cookie)> выполнялся бы как разметка. Сейчас значения вставляются текстовыми узлами, поэтому любая разметка отображается как обычный текст:

function renderRow(label, value) {
  const row = document.createElement('p');
  const strong = document.createElement('strong');
  strong.textContent = `${label}: `;
  row.appendChild(strong);
  row.appendChild(document.createTextNode(String(value)));
  return row;
}

Тест pages #9 проверяет это статически: в userinfo.html не должно встречаться присваивание .innerHTML =.

Где innerHTML остался и почему это допустимо

В index.html он используется для очистки контейнеров (= "") и вставки статической разметки без пользовательских данных. Названия навыков и заданий выводятся через innerText и createElement. Правило простое: разметка — литералом в коде, данные — только текстом.

Валидация входных данных

// 1. Проверяем тип, а не только наличие
const username = typeof body?.username === 'string' ? body.username.trim() : '';

// 2. Проверяем формат регулярным выражением с явными границами длины
const USERNAME_RE = /^[A-Za-zА-Яа-яЁё0-9_.-]{3,32}$/u;

// 3. Пересобираем объект из проверенных полей, а не пишем присланный целиком
user.profile = { level, xp, skills: skills.slice(0, 200) };

Третий пункт защищает от «загрязнения» записи: клиент не может дописать в свой профиль произвольные поля, например isAdmin. Числа проверяются Number.isFinite, что отсекает строки, NaN и Infinity.

Компромисс, о котором нужно знать

Выключенные CSP и frameguard — это осознанная уступка ради CDN-стилей и работы во встроенном превью. Для публичного продакшена стоит перенести Tailwind и Font Awesome в локальные файлы, вынести инлайновые скрипты в отдельные .js и включить обе защиты обратно.

Что не защищено и почему

Нет CSRF-токенов

Опоры две: sameSite: 'lax' и то, что все изменяющие операции — POST/PUT с Content-Type: application/json, который нельзя отправить простой HTML-формой. Для строгого продакшена стоит добавить токены (csurf или double-submit cookie).

Rate limit по IP в памяти

Счётчики живут в памяти процесса: рестарт обнуляет их, а несколько инстансов считают независимо. За NAT один лимит делят все пользователи. Решение — общий store (Redis).

Нет подтверждения почты и восстановления пароля

Учётка — это только логин и пароль. Забытый пароль восстановить невозможно: хеш необратим, а сбрасывать его некуда отправлять.

Нет ролей и прав

Все пользователи равны, админов нет. Каждый может менять только свой профиль — проверка идёт по req.session.username, чужой логин в теле запроса игнорируется.

Игровые данные не защищены

Навыки и задания лежат в localStorage: пользователь может открыть DevTools и поставить себе 99-й уровень. Это одиночная игра-трекер — жульничество вредит только самому игроку.

Файл вместо базы

При десятках одновременных регистраций возможна потеря записи: между readUsers и writeUsers нет блокировки. Атомарная запись спасает от повреждения файла, но не от гонки.

Чек-лист перед продакшеном

  • Задать SESSION_SECRET длиной не менее 32 байт из менеджера секретов.
  • Выставить NODE_ENV=production и терминировать HTTPS на реверс-прокси.
  • Перенести хранилище сессий в Redis, иначе рестарт разлогинивает всех.
  • Перенести учётки в СУБД с уникальным индексом по логину.
  • Локализовать CDN-ресурсы и включить CSP и frameguard.
  • Настроить app.set('trust proxy', 1), чтобы rate limit видел реальный IP клиента за прокси.
  • Добавить журналирование неудачных входов и мониторинг всплесков 401 и 429.
  • Держать users.json вне репозитория и включить его в резервное копирование.
