Константы и настройки

const PORT = Number(process.env.PORT) || 3000;
const HOST = process.env.HOST || '0.0.0.0';
const USERS_FILE = process.env.USERS_FILE || path.join(__dirname, 'users.json');
const BCRYPT_ROUNDS = Number(process.env.BCRYPT_ROUNDS) || 10;

const USERNAME_RE = /^[A-Za-zА-Яа-яЁё0-9_.-]{3,32}$/u;
const MIN_PASSWORD_LENGTH = 6;
const MAX_PASSWORD_LENGTH = 128;
  • HOST = '0.0.0.0' — сервер слушает все интерфейсы. Внутри Docker или превью-среды привязка к 127.0.0.1 сделала бы приложение недоступным снаружи контейнера.
  • USERS_FILE через переменную — благодаря этому тесты подставляют временный файл во временной директории и не портят рабочие данные.
  • BCRYPT_ROUNDS = 10 — компромисс: около 50–100 мс на хеш. Тесты понижают до 4, иначе прогон становится ощутимо медленнее.
  • Верхняя граница пароля 128 — bcrypt всё равно учитывает только первые 72 байта, а без лимита можно было бы прислать мегабайтную строку и заставить сервер её хешировать.

Работа с файлом-хранилищем

readUsers()

readUsers(): User[]
function readUsers() {
  try {
    const raw = fs.readFileSync(USERS_FILE, 'utf8').trim();
    if (!raw) return [];

    const parsed = JSON.parse(raw);
    return Array.isArray(parsed) ? parsed : [];
  } catch (error) {
    if (error.code === 'ENOENT') return [];

    console.error(`Не удалось прочитать ${USERS_FILE}:`, error.message);
    return [];
  }
}

Функция обязана быть непробиваемой: она вызывается в каждом запросе к API. Обрабатываются четыре ситуации — файла нет (ENOENT), файл пуст, внутри не массив, внутри синтаксически битый JSON. Во всех случаях возвращается пустой массив, а сервер продолжает работать.

Исправленный краш

В исходной версии было JSON.parse(fs.readFileSync(usersFilePath)) без обработки ошибок, а в репозитории лежал пустой users.json. JSON.parse('') бросает SyntaxError, и первый же запрос к /register ронял процесс. Теперь на это есть тест server #1: «пустой users.json не роняет сервер».

writeUsers()

writeUsers(users: User[]): void
function writeUsers(users) {
  const tmpFile = `${USERS_FILE}.${process.pid}.tmp`;
  fs.writeFileSync(tmpFile, JSON.stringify(users, null, 2), 'utf8');
  fs.renameSync(tmpFile, USERS_FILE);
}

Запись атомарная: сначала полный файл во временное имя, затем rename — на POSIX-системах это атомарная операция. Если процесс упадёт в середине записи, на диске останется либо старая, либо новая версия, но не половина JSON. В имени временного файла есть process.pid, чтобы два процесса не мешали друг другу.

publicUser(), createProfile(), findUser()

function publicUser(user) {
  return { username: user.username, profile: user.profile, createdAt: user.createdAt };
}

function createProfile() {
  return { level: 1, xp: 0, skills: [] };
}

function findUser(users, username) {
  const normalized = String(username).toLowerCase();
  return users.find((user) => String(user.username).toLowerCase() === normalized);
}
  • publicUser — «белый список» полей. Единственный способ, которым пользователь попадает в ответ, поэтому passwordHash утечь не может.
  • createProfile — фабрика: возвращает новый объект каждому пользователю. Если бы профиль был константой, все пользователи делили бы одну ссылку.
  • findUser — поиск регистронезависимый, поэтому нельзя зарегистрировать Hunter при существующем hunter и обмануть проверку уникальности. String() защищает от значения не-строки в теле запроса.

validateCredentials()

validateCredentials(body: unknown): string | null // текст ошибки или null
const username = typeof body?.username === 'string' ? body.username.trim() : '';
const password = typeof body?.password === 'string' ? body.password : '';

if (!username || !password) {
  return 'Укажите логин и пароль.';
}
if (!USERNAME_RE.test(username)) {
  return 'Логин: 3–32 символа, буквы, цифры и символы _ . -';
}
if (password.length < MIN_PASSWORD_LENGTH || password.length > MAX_PASSWORD_LENGTH) {
  return `Пароль должен быть от ${MIN_PASSWORD_LENGTH} до ${MAX_PASSWORD_LENGTH} символов.`;
}
return null;

Проверка типов через typeof обязательна: клиент может прислать {"username": {"$ne": null}} или число. Логин обрезается по краям, но пароль — никогда: пробелы в пароле значимы. Возврат строки-ошибки вместо исключения делает код маршрутов линейным: const error = validateCredentials(req.body); if (error) return res.status(400)…

Middleware

helmet

app.use(
  helmet({
    // Страницы подключают Tailwind/Font Awesome с CDN, а сам сайт может
    // открываться во встроенном превью — поэтому CSP и frameguard выключены.
    contentSecurityPolicy: false,
    frameguard: false,
    crossOriginEmbedderPolicy: false,
    crossOriginResourcePolicy: false,
  })
);

Остаются включёнными X-Content-Type-Options: nosniff, Referrer-Policy, Strict-Transport-Security и другие. Четыре опции отключены осознанно: строгий CSP заблокировал бы Tailwind с CDN и инлайновые скрипты страниц, а frameguard запретил бы открывать приложение во встроенном iframe-превью.

Как включить CSP правильно

Нужно перенести Tailwind и Font Awesome в локальные файлы, вынести инлайновые скрипты в assets/*.js и затем задать политику вида default-src 'self'. Тогда contentSecurityPolicy можно вернуть.

Ограничение частоты

const authLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  limit: 20,
  standardHeaders: 'draft-7',
  legacyHeaders: false,
  message: { success: false, message: 'Слишком много попыток. Повторите позже.' },
});

20 попыток за 15 минут с одного IP — этого достаточно человеку и мало для перебора паролей. Лимитер вешается только на три маршрута аутентификации: чтение статики и /api/me не ограничены. Ответ при превышении — 429 в том же JSON-формате, что и остальные ошибки.

Маршруты

registerHandler

async function registerHandler(req, res, next) {
  try {
    const error = validateCredentials(req.body);
    if (error) return res.status(400).json({ success: false, message: error });

    const username = req.body.username.trim();
    const users = readUsers();

    if (findUser(users, username)) {
      return res.status(409).json({ success: false, message: 'Пользователь с таким логином уже существует.' });
    }

    const user = {
      username,
      passwordHash: await bcrypt.hash(req.body.password, BCRYPT_ROUNDS),
      profile: createProfile(),
      createdAt: new Date().toISOString(),
    };

    users.push(user);
    writeUsers(users);

    req.session.username = user.username;
    return res.status(201).json({ success: true, message: 'Регистрация успешна', user: publicUser(user) });
  } catch (err) {
    return next(err);
  }
}

Порядок шагов важен: сначала дешёвая валидация, потом чтение файла, и только затем дорогой bcrypt.hash() — так невалидные запросы не нагружают процессор. После успешной регистрации пользователь сразу авторизован: в сессию кладётся только username, а не весь объект, чтобы данные не устаревали.

loginHandler

const users = readUsers();
const user = findUser(users, req.body.username.trim());

// Одинаковый ответ для «нет пользователя» и «неверный пароль»,
// чтобы нельзя было перебором узнать существующие логины.
const ok = user ? await bcrypt.compare(req.body.password, user.passwordHash) : false;
if (!ok) {
  return res.status(401).json({ success: false, message: 'Неверный логин или пароль.' });
}

req.session.username = user.username;
return res.json({ success: true, message: 'Вход выполнен', user: publicUser(user) });

bcrypt.compare() сравнивает хеши за постоянное время, поэтому по длительности ответа нельзя догадаться, совпал ли префикс пароля. Формулировка ошибки намеренно общая — «Неверный логин или пароль»: она не подтверждает существование учётки.

GET /api/me

app.get('/api/me', (req, res) => {
  if (!req.session.username) {
    return res.status(401).json({ success: false, message: 'Не авторизован' });
  }

  const user = findUser(readUsers(), req.session.username);
  if (!user) {
    return req.session.destroy(() =>
      res.status(401).json({ success: false, message: 'Не авторизован' })
    );
  }

  return res.json({ success: true, user: publicUser(user) });
});

Второй случай — «сессия есть, а пользователя уже нет» (например, запись удалили из файла вручную). Тогда сессия уничтожается, чтобы клиент не оставался в подвешенном состоянии.

PUT /api/me/profile

const { level, xp, skills } = req.body ?? {};
if (!Number.isFinite(level) || level < 1 || !Number.isFinite(xp) || xp < 0 || !Array.isArray(skills)) {
  return res.status(400).json({ success: false, message: 'Некорректный профиль.' });
}

user.profile = { level, xp, skills: skills.slice(0, 200) };
writeUsers(users);

Number.isFinite отсекает строки, NaN и Infinity. Профиль пересобирается из трёх проверенных полей — прислать лишние ключи и записать их в файл нельзя. slice(0, 200) ограничивает размер массива навыков.

POST /api/logout

app.post('/api/logout', (req, res) => {
  req.session.destroy(() => {
    res.clearCookie('sl.sid');
    res.json({ success: true, message: 'Выход выполнен' });
  });
});

Сессия удаляется на сервере, а не только «забывается» браузером: даже если куку перехватили, после выхода она бесполезна. Метод POST, а не GET — чтобы выход нельзя было вызвать простым переходом по ссылке или загрузкой картинки.

POST /register — устаревший алиас

app.post('/register', authLimiter, (req, res, next) => {
  const exists = Boolean(findUser(readUsers(), req.body?.username ?? ''));
  return exists ? loginHandler(req, res, next) : registerHandler(req, res, next);
});

Старый эндпоинт вёл себя как «войти или зарегистрировать». Чтобы не ломать внешних клиентов, поведение сохранено, но теперь оно реализовано вызовом тех же обработчиков — с хешированием, валидацией и rate-лимитом. Именно ради этого маршрута логика вынесена в именованные функции registerHandler и loginHandler, а не написана прямо в app.post().

Статика, 404 и ошибки

app.use(express.static(__dirname, { extensions: ['html'] }));

app.use('/api', (req, res) => {
  res.status(404).json({ success: false, message: 'Метод не найден' });
});

app.use((err, req, res, next) => {
  console.error('Необработанная ошибка:', err);
  res.status(500).json({ success: false, message: 'Внутренняя ошибка сервера' });
});

if (require.main === module) {
  app.listen(PORT, HOST, () => {
    console.log(`Сервер запущен на http://localhost:${PORT}`);
  });
}

module.exports = app;
  • extensions: ['html'] — /login отдаёт login.html, расширение в адресе необязательно.
  • Статика после API — иначе файл с именем как у маршрута мог бы перехватить запрос.
  • JSON-404 для /api — клиент всегда получает предсказуемый JSON, а не HTML, который сломает response.json().
  • Четыре аргумента у обработчика ошибок — обязательное условие Express, иначе он будет воспринят как обычный middleware. Стек пишется в лог сервера, наружу уходит нейтральный текст.
  • require.main === module — сервер слушает порт только при прямом запуске. Тесты импортируют app и поднимают его на случайном свободном порту.
